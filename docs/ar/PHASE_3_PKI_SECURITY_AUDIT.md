# تدقيق مركز — mTLS وPKI

**نطاق المراجعة:** `config/generate-dev-certs.js` و`shared/mtls.js` واختبارات mTLS.
**قاعدة المراجعة:** لم يُعدّل أي كود أثناء الجلسة.
**الحكم المؤقت:** توجد نتيجة HIGH ونتيجة MEDIUM يجب إصلاحهما قبل APIs الخوادم.

## ما اجتاز التدقيق

| البند | النتيجة | الدليل |
|---|---|---|
| مصادقة ثنائية | PASS | `requestCert: true` و`rejectUnauthorized: true` على الخادم. |
| تحقق العميل من CA | PASS | `rejectUnauthorized: true` وCA محددة في العميل. |
| منع النقل غير المشفر داخلياً | PASS | `mtlsRequest` يرفض كل protocol عدا `https:`. |
| هوية تطبيقية | PASS | لا يُكتفى بالمصافحة؛ يتحقق التطبيق من CN/SAN للدور المطلوب. |
| TLS قديم | PASS | `minVersion: TLSv1.3`. |
| اختبارات السلوك | PASS | نجاح server1→server2 ورفض توقع هوية server3 عند الاتصال بـserver2. |
| قبول شهادة node بديل | PASS تصميمياً | endpoint يطلب الدور الصريح ولا يعتمد فقط على أي شهادة موقعة من CA. |

## النتائج عالية الخطورة

1. **[HIGH] لا توجد آلية إلغاء شهادات مفروضة في نمط الإنتاج.**

   | البند | التحليل |
   |---|---|
   | الموقع | `shared/mtls.js`، دالة `loadMtlsMaterial` وخيارات TLS. |
   | المشكلة | تتحقق المصافحة من سلسلة الثقة والصلاحية، لكن لا تُحمّل CRL ولا تُلزمها في الإنتاج. شهادة node مسروقة تظل مقبولة حتى انتهاء صلاحيتها. |
   | الأثر | مهاجم يحمل مفتاحاً خاصاً وشهادة صالحة لعقدة يمكنه الانتحال ضمن فترة صلاحيتها. |
   | سيناريو الاستغلال | سرقة شهادة server1؛ المهاجم يتصل إلى Server 2 بشهادة ما زالت موقعة من CA ولا توجد قائمة إلغاء تمنعها. |
   | الإصلاح المطلوب | دعم `MTLS_CRL_PATH` وتحميله في خادم وعميل TLS، ورفض إقلاع الإنتاج في غيابه. توثيق تجديد وإصدار CRL. |

## النتائج المتوسطة

1. **[MEDIUM] لا يفحص محمل مواد mTLS صلاحيات المفتاح الخاص محلياً.**

   | البند | التحليل |
   |---|---|
   | الموقع | `shared/mtls.js`، دالة `readPem`. |
   | المشكلة | يقبل التطبيق private key يمكن أن تكون صلاحياته واسعة على أنظمة POSIX. |
   | الأثر | قد يستطيع مستخدم محلي آخر نسخ شهادة العقدة ومفتاحها وانتحالها. |
   | الإصلاح المطلوب | فحص صلاحيات `keyPath` في POSIX ورفض أي group/world read/write/execute؛ تطبيق صلاحية `0600` في سكربت الشهادات والتوثيق. |

## قرار المعالجة

> لا يجوز الانتقال إلى Phase 4 قبل علاج النتيجتين. سيُضاف تحقق CRL إلزامي للإنتاج وفحص صلاحية private key دون تخفيف `rejectUnauthorized` أو هوية CN/SAN.

## إغلاق النتائج بعد المراجعة

بعد توثيق النتيجتين، أضيف دعم `crl` إلى مواد TLS لكلا طرفي الاتصال. نمط الإنتاج يفشل قبل فتح أي منفذ عندما يغيب `MTLS_CRL_PATH`. كذلك يتحقق محمل key PEM في POSIX من عدم وجود أي صلاحيات group/world. أُضيف اختبار `production mTLS configuration fails closed without a CRL`، ونجحت اختبارات التكامل الثلاث.

| النتيجة | الحالة بعد الإصلاح | التحقق |
|---|---|---|
| HIGH-1: غياب CRL | CLOSED | اختبار إنتاج بلا CRL يفشل مغلقاً. |
| MEDIUM-1: صلاحيات private key | CLOSED | شرط `mode & 0o077 == 0` في POSIX، وشهادات التطوير تكتب بمود `0600`. |

> **حكم نقطة التدقيق:** PASS. لا توجد نتائج CRITICAL أو HIGH أو MEDIUM مفتوحة في مراجعة mTLS/PKI، ويمكن الانتقال إلى Phase 4.
